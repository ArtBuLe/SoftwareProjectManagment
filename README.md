1. Название проекта
Разработка консольной игры «Тетрис» на языке C#.

2. Краткое описание проекта
Создание десктопного консольного приложения, реализующего классические механики игры «Тетрис» (падение фигур, повороты, очистка линий, подсчёт очков) на языке C#. Проект выполняется в сжатые сроки (1–2 недели) для использования в учебных целях и пополнения портфолио.

3. Анализ требований
- Насколько понятны требования: Требования абсолютно понятны, т.к. правила классического «Тетриса» общеизвестны.
- Может ли заказчик менять требования: Вероятность изменений минимальна, объём работ жёстко зафиксирован на этапе концепции.
- Можно ли разделить продукт на отдельные функциональные части: Да, игру легко разделить на независимые модули (отрисовка поля, логика фигур, система очков).
- Нужно ли регулярно показывать промежуточные результаты: Да, демонстрация работающей базовой версии поможет выявить проблемы с управлением или отрисовкой в консоли на раннем этапе.
- Насколько критичны сроки: Сроки критичны (1–2 недели).

4. Сравнение моделей

| Модель | Как будет организована разработка | Преимущества | Недостатки |
| - | - | - | - |
| Waterfall | Строго последовательно: сначала полное ТЗ, потом весь код, потом тестирование, потом сдача. | Простота планирования для небольшого проекта, чёткие этапы. | Рабочая версия игры появится только в конце срока, риск обнаружить фатальную ошибку архитектуры слишком поздно. |
| Итерационная | Создание прототипа всей игры сразу, затем цикличное улучшение графики, логики и удобства. | Раннее выявление проблем с игровым процессом, постоянное улучшение качества. | Сложно оценить прогресс, возможна бесконечная доработка одного и того же функционала в условиях сжатых сроков. |
| Инкрементальная | Поэтапное добавление функций: сначала базовое падение, потом повороты, потом очки, потом уровни. | Раннее получение минимально работающей версии, высокая мотивация, лёгкое тестирование новых функций. | Требуется продуманная архитектура с самого начала, чтобы новые части легко встраивались в старые. |

5. Выбранная модель
Инкрементальная модель разработки.

6. Обоснование выбора
Особенности проекта, повлиявшие на выбор: проект имеет очень сжатые сроки (1–2 недели) и стабильные, неизменные требования. Разработка игры «с нуля до конца» без промежуточных результатов скрывает ошибки консольной отрисовки и логики до самого финала.
Преимущества выбранного подхода: инкрементальная модель позволяет уже через несколько дней получить минимально работающую версию игры (например, падающую фигуру), которую можно запустить и проверить. Это даёт быструю обратную связь и позволяет тестировать архитектуру кода на ранних этапах. Каждая следующая часть логически надстраивается над предыдущей, что идеально ложится на объектно-ориентированную структуру C#.
Возможные ограничения: необходимо сразу заложить гибкую архитектуру классов (например, отдельный класс для поля и отдельный для фигур), иначе добавление новых механик на поздних этапах потребует переписывания кода, что недопустимо при сроке в 1–2 недели.

7. Предварительный план разработки

Инкремент 1: Базовое игровое поле и механика падения (2–3 дня)
- Реализация отрисовки пустого поля 10x20 в консоли.
- Создание класса одной фигуры.
- Реализация её автоматического падения вниз и базового управления с клавиатуры (влево, вправо).

Инкремент 2: Полноценная система фигур и коллизий (3–4 дня)
- Добавление всех 7 классических тетромино.
- Реализация логики поворота фигур.
- Внедрение системы проверки коллизий (столкновение со стенами, дном и другими фигурами), остановка фигуры при касании.

Инкремент 3: Игровая логика и завершение игры (3–4 дня)
- Реализация алгоритма поиска и удаления заполненных линий.
- Сдвиг поля вниз после очистки линии.
- Внедрение системы подсчёта очков и условия завершения игры (Game Over).

Инкремент 4: Полировка, уровни сложности и финальная сборка (2–3 дня)
- Добавление системы уровней: увеличение скорости падения фигур при наборе определённого количества очков.
- Улучшение пользовательского интерфейса в консоли (отображение счёта, следующей фигуры, инструкций).
- Финальное тестирование, исправление багов и компиляция в готовый исполняемый файл.
