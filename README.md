**Практическая работа №2. План реагирования и контроль проекта**

**Разделение обстоятельств на проблемы и риски:**

1. Backend-разработчик отстаёт от графика на три дня - проблема задержки разработки
2. Frontend-разработчик не может подключить интерфейс к API - проблема интеграции
3. Тестировщик не получил готовую сборку - проблема блокировки тестирования
5. Обнаружена ошибка в структуре хранения расписания - проблема качества архитектуры

Потенциальные риски:

4. Заказчик попросил добавить новую функцию — экспорт расписания в PDF. - риск изменения требований
6. Резервное копирование базы данных не настроено. - риск потери данных

**План реагирования на каждое обстоятельство:**

1. Backend отстаёт на 3 дня:
- Пересмотреть приоритеты задач backend-разработчика
- Передать тестировщику часть задач по написанию тест-кейсов
- Рассмотреть возможность упрощения некритичного функционала
- Ежедневный контроль прогресса

2. Frontend не может подключиться к API:
- Немедленно согласовать контракт API с backend-разработчиком
- Перевести frontend на использование mock API до готовности реального бэкенда
- Продолжить разработку интерфейса параллельно

3. Тестировщик не получил сборку:
- Передать тестировщику доступ к промежуточной сборке для написания тест-кейсов
- Начать тестирование доступных модулей
- Подготовить тестовую документацию параллельно с разработкой

4. Заказчик просит экспорт в PDF:
- Зафиксировать изменение требований официально
- Оценить влияние на сроки (добавит минимум 2-3 дня работы)
- Предложить перенести функцию в следующий релиз после демонстрации
- Если функция критична - пересмотреть план и сократить менее приоритетный функционал

5. Ошибка в структуре БД:
- Немедленно исправить структуру до продолжения разработки
- Создать резервную копию текущей БД перед изменениями
- Оценить влияние на существующий код и внести необходимые правки
- Приоритет - критический, так как влияет на всю систему

6. Резервное копирование не настроено:
- Настроить автоматическое резервное копирование в течение текущего дня
- Ответственный - backend-разработчик или системный администратор
- Это критическая задача безопасности данных

**План контроля на оставшиеся 10 рабочих дней:**

|Контрольная точка|Срок|Что проверяется|Ответственный|
|---|---|---|---|
|Согласование контракта API|День 1|Документация API готова, frontend работает с mock|Backend + Frontend|
|Исправление структуры БД|День 2|Структура БД исправлена, резервное копирование настроено|Backend|
|Backend наверстал отставание|День 5|Отставание устранено, API готово для интеграции|Backend|
|Интеграция frontend и backend|День 6|Frontend подключен к реальному API|Frontend + Backend|
|Передача сборки тестировщику|День 7|Тестировщик получил рабочую сборку|Backend|
|Завершение тестирования|День 9|Все критические баги исправлены|Тестировщик|
|Готовность к демонстрации|День 10|Проект готов к показу заказчику|Руководитель|

**Дополнительные меры контроля:**
- Ежедневные 15-минутные обсуждения для отслеживания прогресса
- Обновление статусов задач в трекере в конце каждого дня
- Еженедельный отчет руководителю о прогрессе и новых рисках
- Готовность пересмотреть план при возникновении новых проблем
